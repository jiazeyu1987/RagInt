# Product Sense

RagInt 当前不是一个单点问答应用，而是一套围绕“展厅讲解”场景扩展出来的前后台系统。

## 核心问题

- 讲解员需要在导览过程中持续输出内容，但不能被固定脚本绑死。
- 观众会在讲解中途插问，系统必须支持打断、接续和上下文延续。
- 展厅需要把一次成功讲解沉淀为可回放资产，而不是每次都从零生成。
- 现场运维需要看到设备状态、控制指令和基础诊断，而不是只依赖人工排查。

## 当前产品形态

### 1. 实时问答

- 用户可以通过文本输入或语音输入发起问答。
- 后端通过 [`/api/ask`](../backend/openapi.json) 进行 SSE 输出，前端再接 TTS 和 UI 状态。
- 系统支持会话名、agent 模式、问题优先级、问答历史和缓存音频复用。

### 2. 展厅导览

- 导览不是固定 PPT，而是“站点列表 + 时长/字数目标 + 风格/画像”驱动的动态讲解。
- 前端围绕 `tour`、`recording`、`playback` 三种模式组织 UI 和运行编排。
- 后端提供站点模板、导览规划、导览控制命令和导览指令解析能力。

### 3. 录制与回放

- 一次导览可以录制 RagFlow 输出片段与对应 TTS 音频。
- 回放模式复用已录制素材，减少现场生成波动。
- 录制资产当前持久化在 `backend/data/recordings/` 及其 SQLite 索引中。

### 4. 运维与诊断

- `/ops` 和 `/api/ops/*` 暴露设备列表、心跳、配置与审计相关入口。
- `/api/status`、`/api/events`、`/api/diagnostics` 构成了基础可观察性入口。

## 目标用户

- 讲解员：关心导览是否顺畅、打断后是否能继续、语音是否稳定。
- 现场运营：关心模板、站点、录制、回放和设备配置是否可控。
- 开发与测试：关心接口、状态、日志、配置和持久化结构是否可定位。

## 当前产品优势

- 实时问答、导览、录制、回放、运维台在同一仓库和同一 UI 编排层中打通。
- 后端对问答、TTS、导览控制、卖点库、问答缓存和录制存档都已有真实实现。
- 前端不仅有页面，还沉淀了 hooks、managers、voice providers 和 e2e 用例。

## 当前产品短板

- 核心编排仍高度集中在 [`fronted/src/app/AppShell.js`](../fronted/src/app/AppShell.js)。
- 真实配置、缓存、录音和历史数据直接落在仓库目录中，治理边界不清。
- 文档体系在本次任务前基本缺失，导致 onboarding 成本高。

## 继续演进时要守住的原则

- 导览体验优先于“功能列表更长”。
- 任何回放和缓存能力都必须可追溯、可解释、可关闭。
- 现场系统的可靠性与安全性不能依赖隐式默认值。
- 文档要跟代码一起演进，而不是事后补作文。
